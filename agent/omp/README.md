# OMP / CLIProxyAPI 运行与切换经验

本页记录可复用的运行时验收经验。具体提供商地址、主机名、账号、令牌和
私有 catalog 必须留在 private overlay，不要写入模板。

## 先分层，再判断

一次请求至少要区分四层：

1. OMP 当前进程实际加载的 provider/base URL；
2. DNS、TLS、反向代理和 Host 路由是否到达正确入口；
3. CLIProxyAPI 是否接受认证请求并完成模型/账号选择；
4. 上游模型是否接受请求内容、地区和账号状态。

`/v1/models`、健康检查、容器 `healthy` 或端口监听只能证明前两层的一部分，
不能证明模型调用成功。最终验收至少要有一次带认证的真实模型请求，并在需要时
覆盖一条 Gemini 和一条 GPT 文本请求；证据只保留模型 ID、HTTP 状态和响应字节数。

## 本次事故沉淀的判断规则

### `400 User location is not supported`

不要仅凭部署机器所在城市判断地区一定符合。这个响应可能由上游账号、账号配额、
上游实际出口、代理入口路由或旧进程仍使用旧 base URL 导致。排查顺序应是：

- 用日志把请求关联到实际 provider、入口 Host、容器版本和响应来源；
- 单独确认代理出口 IP 与账号/上游的地区约束；
- 区分“请求到达了上游但上游拒绝”和“请求没有到达预期入口”；
- 检查 OMP 进程启动时间是否早于 catalog/projection 变更，必要时重启所有相关进程。

未认证的 `/v1/models` 返回 401，通常说明请求已到达认证边界；它仍不等于模型
请求、账号额度或地区验收通过。

### `tool_use` / `tool_result` 配对 400

若上游提示 tool-use ID 没有紧邻的 tool-result，且同一请求重试仍得到同类 400，
这是协议转换、旧版后端或历史长上下文中的确定性问题，不是网络抖动。重试预算
和切换模型不会修复同一份坏 transcript；应检查：

- 每个 `tool_use` 是否在下一条消息中有对应的 `tool_result`；
- 转换层是否保留了配对顺序和消息边界；
- 后端版本是否包含工具调用配对修复；
- 是否有旧 OMP 进程继续指向旧入口。

原始请求和响应日志只用于本机取证，必须脱敏，不要把 Authorization、令牌、完整
请求体、响应体或私有 URL 写入共享 artifact。

### DNS 切换不是完整切换

只修改 DNS 不会自动更新反向代理的 `server_name`、证书、Host 路由，也不会改变
已经启动的 OMP 进程内存中的 base URL。切换期间应：

1. 先在新入口完成 Nginx/TLS/认证和真实模型请求验收；
2. 暂时保留可回滚入口，直到新入口有连续成功证据；
3. 生成并核对 OMP projection 后，统一重启仍持有旧地址的进程；
4. 通过进程启动时间、日志入口和真实请求确认没有旧进程残留。

最终应只保留一个 canonical provider；兼容入口只作为有期限的回滚措施，不能
长期依赖 DNS 把旧 Host “伪装”成新服务。

## 最小验收矩阵

| 检查 | 能证明什么 | 不能证明什么 |
|---|---|---|
| catalog / generated projection | 配置来源和候选模型 | 当前进程已经重新加载 |
| DNS/TLS/反代探测 | 入口与 Host 路由 | 账号、额度、模型可用 |
| 认证 `/v1/models` | 认证边界和模型列表 | 真实生成、工具调用协议 |
| Gemini/GPT 真实请求 | provider/account/upstream 链路 | 长上下文工具历史兼容性 |
| 多工具长上下文请求 | `tool_use`/`tool_result` 转换契约 | 其他 provider 的额度与地区 |
| 容器和 OMP 日志 | 版本、入口、状态码、错误来源 | 单凭健康状态推断业务可用 |

发生 400 时先保存脱敏的请求摘要和 request ID，再把错误按“地区/账号、协议转换、
入口路由、额度/限流、网络”分类；不要用盲目重启或反复重试替代定位。
