# 评分死锁与迭代闭环（实战必读）

目标：将 PRD 评分提升到约定分数（如 80+）。评分是评审线索，需求事实与用户决定才是业务依据；已达目标且评审通过时停止追分。

**评分死锁现象**：保存修订内容并触发「重新评分」后，**首次重算常返回缓存旧分/旧问题清单**（OSS/分析器缓存未即时失效）。两次以上重算且等待 40~60s 后，分数才反映最新内容（2026-11 Story-295367/295522 实测：V1 77.3 → V5 80.8；44.8 → 80.1）。

**迭代闭环（必须跑通）**：
1. dump 锁定基线：记录 `story_code`、模块、当前分数与完整问题清单。
2. 逐项核对问题：先处理致命/重要项；合并同一规则的多条问题；评分建议不证明业务规则存在，缺业务决定时先与用户确认或标注待确认。
3. 定点修订：只修改已识别问题及消除冲突必须同步的引用；同一规则只在一处定义，其余引用；未点名内容保持原样。
4. 保存后**回读**：`fetch` 持久化 `prd.md` 核对关键修复标记，不要只看编辑器或仅凭保存返回。
5. 等待缓存刷新（约 40~60s）再重算；若分数与 issues 仍是旧文，等待或二次重算。
6. 比较分数与问题数，循环至目标。

**常见避坑**：
- 保存接口 `version` 参数可能被忽略（返回恒为 1）；`module_id` 从 `file_path` 的 `module_<id>` 解析。
- 页面「重新评分」按钮（旧版可能叫「重新检测」）；脚本已兼容两文案。
- 覆盖性验收需给可核对的具体数值期望（如比例换算 AC：50mm×比例→期望结果），避免相对表述无法判定。
- 绝对化指标（100%、无误差）需补统计口径与样本，否则不可量化扣分。
- 评分器对**一致性与依据**（维度 d3）极严：同一规则、阈值、生效时点、异常处置必须在全文一致，任何残留矛盾会新自 major/致命问题。
