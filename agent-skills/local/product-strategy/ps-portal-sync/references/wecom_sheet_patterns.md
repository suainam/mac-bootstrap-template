# 企业微信与腾讯文档共享表格操作规范 (WeCom / Tencent Sheet Patterns)

本文档为 `ps-portal-sync` 涉及的企业微信 / 腾讯文档在线表格（`doc.weixin.qq.com/sheet`，如《商品决策平台二期项目推进表》）提供统一的架构认知、Canvas 逆向、合并单元格规约、WBS 结构化维护与防损门禁。

---

## 1. 核心架构认知：Canvas 渲染与对象模型

腾讯文档 / 企业微信在线表格采用 WebGL / 2D Canvas 双层渲染架构，所有单元格网格与文字内容绘制在 `<canvas>` 上，DOM 中仅包含工具栏、浮动编辑框（`CopyPasteDiv`、`#alloy-simple-text-editor`）与选区遮罩。

### 1.1 禁止事项
- **严禁使用 DOM 文本选择器抓取数据**：表格内容未直接挂载在 DOM 节点上，`document.querySelector('td')` 无法获取表格矩阵内容。
- **严禁模拟裸点击与键盘输入盲写**：在 Canvas 上计算物理像素坐标极易受缩放比（DPR）、冻结行列偏移（`frozenRowCount`）及滚动条影响，产生错位写入。

### 1.2 标准数据读取规范
统一通过页面全局暴露的 `SpreadsheetApp` 及其底层数据服务穿透读取：

```javascript
// 提取任意单元格纯文本值的权威范式
const workbook = window.SpreadsheetApp.workbook;
const activeSheet = workbook.activeSheet;
const e2eTools = window.SpreadsheetApp.e2eTools;

// 获取指定行 (0-indexed)、列 (0-indexed) 的格式化编辑值
const cellValue = e2eTools.getCellEditValue(workbook, rowIndex, colIndex);
```

## 2. 合并单元格门禁 (`wbs-structure-gate`)

在进行任何行插入、字段填报或结构调整前，**必须先扫描工作表的合并单元格列表**：

```javascript
const merges = activeSheet.mergeManager.mergeList;
// merges 结构示例：
// { sheetId: 'ma7wxv', startRowIndex: 20, endRowIndex: 37, startColIndex: 1, endColIndex: 1 }
```

### 2.1 典型合并反模式与防踩坑
- **大格冒充多行陷阱**：在产研推进表模板中，列 A（子项目名）、列 B（Q4目标）、列 Q/R/S（周报运营/产研进展）通常为**跨几十行纵向大合并格**（例如 B21:B38 实际是跨 18 行的单一目标格）。
- **红线规则**：
  1. 严禁将大合并格（如 B 列）误当作逐行任务列表覆盖写入！
  2. 任务/需求名称必须写入未合并的明细列（如列 D「里程碑/任务描述」）。
  3. 需求编码必须写入未合并的列 E「需求ID」。

## 3. 项目推进表 WBS 结构模型 (`milestone-demand-model`)

大型产研推进表（如商品决策二期 Q4WBS）统一遵循**「里程碑 + 关联 Demand」**的层级结构：

```text
[子项目: 门店智能组货] (A-B 列跨全子项目大合并)
├── 【里程碑 1】模型与策略
│   ├── Demand-29470 (组货模型可选配置)
│   ├── Demand-31939 (慢病统筹店组群与自有品牌/医保占比模型)
│   ├── Demand-32014 (TOP品种补全与补充主推优化)
│   ├── Demand-31935 (O2O多渠道头部商品扩入组货)
│   └── Demand-32016 (医保统筹店选品补货模型评估)
├── 【里程碑 2】商品准入与编码
│   ├── Demand-31420 (准新品与反季节剔除)
│   ├── Demand-31955 (高库存、效期、统筹过滤条件)
│   ├── Demand-31957 (货源仓禁发过滤条件)
│   └── Demand-28706 (新旧商品编码替换衔接)
...
```

### 3.1 字段映射矩阵

| 列 | 字段名 | 填报规范 | 缺失与异常处置 |
| :--- | :--- | :--- | :--- |
| **A** | 子项目（负责人） | 纵向合并大格，填写子项目名称及整体负责人 | 保留原有业务目标与负责人 |
| **B** | Q4目标 | 纵向合并大格，填写定性/定量考核目标 | 严格保留原件，严禁覆盖 |
| **C** | 类型与状态 | 里程碑行固定为 `【里程碑】`；明细行填写状态（如 `【研发中】`、`【待排期】`、`【未开始】`） | 必须与 DevOps 需求状态保持事实一致 |
| **D** | 里程碑 / 任务 | 里程碑行填写里程碑标题；明细行填写需求标题或任务包简述 | 必须忠实概括需求原文 |
| **E** | 需求ID | 里程碑行填 `-`；明细行填写标准化需求编码（如 `Demand-31957`） | 必须对应真实存在的 DevOps 单号 |
| **F** | 审计月份 | 里程碑行填 `-`；明细行填写效能平台审议月份（如 `2026-09`） | 系统无审议月份记录时**严格留空** |
| **G** | 执行人 | 里程碑行填 `-`；明细行填写需求负责人（如 `南宗帅`） | 多人时如实保留，严禁擅自指派他人 |
| **H** | PRD评审 | 里程碑行填 `-`；明细行填写 PRD 评审完成日期（`planned_review`） | 系统未记录时**严格留空** |
| **I** | 研发提测 | 里程碑行填 `-`；明细行填写计划研发提测日（`dev_end`） | 多工作项时取最晚日期；无日期留空 |
| **J** | 测试通过 | 里程碑行填 `-`；明细行填写计划测试完成日（`test_end`） | 计划节点不代表实际验收通过；无日期留空 |
| **K** | 预完成时间 | 里程碑行填 `-`；明细行填写到期日（`due`） | 多工作项取最晚日期；无日期留空 |
| **L** | 业务UAT | 里程碑行填 `-`；明细行填写 UAT 验收日期 | 暂无系统记录时**严格留空** |
| **N** | 进度 | 里程碑行留空；明细行填写当前进度百分比（如 `60%`） | 必须有真实产研进度支撑，禁止随意臆造 |
| **O** | 整体进度 | 里程碑行绑定公式 `=AVERAGE(N_start:N_end)` | 公式引用的明细行区间必须严格对齐 |
| **P** | 备注（产研） | **不填**。Story/JIRA 等追溯信息留在 `01_source_data` 底稿 | 已有内容用 `--clear-range` 清空 |
| **Q/R/S** | 运营/产研/指标 | 纵向合并大格，分别记录系统运营、信息系统周进展、实际业务 KPI 指标 | 保留既有汇报内容，只追加增量进展 |

## 4. 行容量与安全增行门禁 (`row-capacity-gate`)

### 4.1 需求与行数守恒定律
- 设定 $M$ 为里程碑总数，$D$ 为不重复的真实需求单总数。
- 所需物理行数 $R_{needed} = M + D$。
- 若现有模板预留行数 $R_{existing} < R_{needed}$，**必须在最后一个明细行后显式插入差额行 $\Delta R = R_{needed} - R_{existing}$**。
- **禁止行为**：严禁为了迎合既有行数限制，而将不同业务逻辑的多个需求强行合并为一个所谓的“任务包”！

### 4.2 结构防破损校验
增行后必须核查：
1. **后续子项目无漂移**：检查下方相邻子项目（如 `空间陈列智能化`）起始行号是否平移，首行标识文本（列 A）是否完整无损。
2. **公式区间同步平移**：检查各里程碑在 O 列的 `=AVERAGE(...)` 计算公式是否已完整覆盖其所属的所有明细行。
3. **大格合并区间重划**：确保 A、B、Q、R、S 列的大合并区域的 `endRowIndex` 正确下推，无残留孤儿空白格。
